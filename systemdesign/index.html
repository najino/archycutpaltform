02 / محصول

پلتفرم عملیات استودیو تدوین

وب و PWA

سه پورتال جدا: مدیر، ادیتور، کارفرما. تسک، پروژه، فاکتور، تنظیمات.

بات تلگرام

دعوت، تحویل فایل، تأیید، اعلان. ویدیو روی سرور ذخیره نمی‌شود.

مالی شمسی

قیمت واحد، اسنپ‌شات روی approve، فاکتور ماهانه، PDF و چاپ.

منبع حقیقت یک دیتابیس است. منطق کسب‌وکار فقط در packages/core نوشته می‌شود.

03 / اصول

قوانینی که معماری را قفل می‌کنند

۱. دامنه واحد

وب و بات برای mutation منطق جدا ندارند. هر تغییر از core و permissions.can می‌گذرد.

۲. یک منبع داده

Postgres تنها منبع حقیقت است. فایل رسانه فقط file_id تلگرام است.

۳. ردپا

هر عمل در activity_log با منبع web / bot / system ثبت می‌شود.

۴. رشد بدون rewrite

فرانت فعلاً جدا نمی‌شود. مرز دامنه طوری است که بعداً API روی همان ماژول‌ها بنشیند.

04 / تصمیم معماری

مونولیت ماژولار · API-محور

یک بک‌اند دامنه، چند کلاینت. این یک پترن تکی GoF نیست؛ سبک سیستم است.

الان

Next و بات مستقیماً core را صدا می‌زنند. جداسازی UI/API الزامی نیست.

مرز آماده

دامنه‌ها در پوشه جدا هستند تا فردا فقط یک Facade HTTP اضافه شود.

بعداً در صورت نیاز

ورکر PDF/کرون، سپس در صورت محصول دوم استخراج API.

09 / جریان اصلی

از تسک تا تسویه

todo← in_progress← delivered← approved

rejected از delivered برمی‌گردد به in_progress. بعد از فاکتور، تسک قفل ویرایش است.

قیمت

روی approve از پروژه/override اسنپ می‌شود. مبلغ bigint تومان است.

فاکتور

دوره شمسی YYYY-MM. یکتایی (user, period). کارفرما فقط خطوط پروژهٔ خودش را می‌بیند.

تحویل

فقط در تلگرام. سرور بایت ویدیو نگه نمی‌دارد؛ copyMessage به کانال.

10 / داده و زنده بودن

Postgres ستون فقرات است

موجودیت‌های کلیدی

users، invite_codes، projects، tasks، deliverables، invoices / invoice_lines، activity_log، bot_sessions، tg_processed_updates.

Realtime

pg_notify('events') → SSE در /api/events. به کلاینت فقط نوع رویداد می‌رود، نه payload داخلی.

پول اعشاری ذخیره نمی‌شود. هفته در DB به ISO است؛ برچسب UI شمسی است.

11 / امنیت

سطح کنترل هویت

نشست

JWT در کوکی httpOnly، sameSite=lax، secure در production. کاربر غیرفعال = خارج.

ورود

scrypt، پیام خطای یکسان، محدودیت ۸/۱۵ دقیقه، وریفای تلگرام با hash و auth_date.

مرز کارفرما

فاکتور و پروژه فقط با clientId. PDF همان فیلتر دامنه را اعمال می‌کند.

لوگوی آژانس فقط تصویر شطرنجی مجاز است. وبهوک بات با secret و idempotency روی update_id.

13 / پترن‌ها

چه پترنی داخل این معماری است

Modular / Bounded Context

مالی از تسک جدا؛ هویت از کاتالوگ جدا.

Layered (نرم)

UI → core → db. صفحه نباید SQL بنویسد.

Facade (آینده)

HTTP نسخه‌دار روی همین ماژول‌ها، وقتی فرانت جدا شد.

RBAC

owner / admin / editor / client با جدول اقدام‌ها.

Worker

PDF همین حالا جداست؛ کرون بات هم جدا از درخواست کاربر است.

Client–Server

سبک استقرار نهایی، نه الزام امروز.

14 / مسیر رشد

سه‌گام؛ بدون جداسازی اجباری

الان — انجام شد

مرز دامنه در core. قرارداد وب/بات پایدار. PDF ورکر. امنیت ورود.

قدم بعد در صورت فشار

صف برای PDF/کرون/اعلان. Redis برای نرخ‌محدود چنداینستنس.

وقتی محصول دوم آمد

Facade HTTP و انتقال Next به کلاینت خالص. میکروسرویس پیش‌فرض نیست.

معیار جدا کردن فرانت: وابستگی صفحات به db() به صفر برسد — نه تاریخ تقویم.

15 / خارج از محدوده

عمداً این‌ها معماری نهایی نیستند

میکروسرویس کامل

تسک و فاکتور تراکنش مشترک دارند. خرد کردن الان هزینه است نه مقیاس.

CQRS / Event Sourcing

حجم رویداد و تیم برای این الگو کافی نیست.

Hexagonal در هر فایل

abstraction بدون مصرف‌کنندهٔ دوم فقط خواندن را سخت می‌کند.

دو منبع حقیقت

دیتابیس جدا برای بات و وب ممنوع است.

16 / جمع‌بندی

یک دامنه. چند کلاینت. یک دیتابیس.

ARSHYCUT یک مونولیت ماژولار است. پترن رشدش Facade روی همین دامنه است، نه شکستن محصول.
